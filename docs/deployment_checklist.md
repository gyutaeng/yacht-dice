# 배포 준비 체크리스트 (3-3)

정식으로(또는 베타로) 배포할 빌드를 만들기 직전에 이 목록을 확인한다.

**베타 배포 후 바뀐 것(사용자 지적)**: 예전엔 `build_info.gd`의
`DEBUG_MODE` 상수를 손으로 `true`/`false`로 고쳐서 배포했는데, "다시
켜는 걸 잊거나 켠 채로 내보내는 사고"가 반복될 위험이 있었다(사람이
기억하는 방식은 이 프로젝트에서 여러 번 실패했다). 지금은 **어느
export 프리셋을 선택하느냐가 DEBUG_MODE를 자동으로 결정한다** - 손으로
상수를 고칠 필요 자체가 없어졌다. 자세한 메커니즘은 `build_info.gd`의
주석과 `docs/web_export.md`의 "DEBUG_MODE 자동 전환" 참고.

## 1. 올바른 export 프리셋을 골랐는지 확인

`export_presets.cfg`에 웹 프리셋이 두 개 있다:

- **`Web (dev)`** - `custom_features=""`. DEBUG_MODE가 켜진 채로
  나온다(디버그 단축키/버튼/화면 로그 전부 보임). 평소 개발 중 확인용.
- **`Web (release)`** - `custom_features="yd_release"`. 이 태그가 있으면
  `build_info.gd`의 `DEBUG_MODE`가 자동으로 `false`가 된다. **베타/정식
  배포는 반드시 이 프리셋으로 export한다.** export_path는
  `F:/Godot/web_build/index.html`로 고정되어 있다 - **이 폴더가 곧
  GitHub Pages 저장소**(이 프로젝트 git과는 무관한 별도 저장소)이므로,
  여기 들어있는 건 항상 배포 빌드뿐이다(개발용은 아래처럼 완전히 다른
  폴더 `F:/Godot/web_dev`를 쓴다 - 섞일 경로 자체가 없음).

가장 간단한 방법은 `F:\Godot\build_release.bat`을 더블클릭하는 것이다
(아래 참고). 직접 CLI로 하려면:

```
"F:\Godot\Godot_v4.7.2-stable_win64.exe" --headless --path "F:\Godot\Project\yacht-dice" --export-release "Web (release)" "F:/Godot/web_build/index.html"
```

export가 끝나면 콘솔에 `BuildStamp: 배포용 빌드(yd_release 태그 있음) -
DEBUG_MODE 꺼짐`이 찍힌다(`addons/build_stamp`가 export 시점에 바로
알려준다) - **이 줄이 "개발용 빌드"로 찍히면 프리셋을 잘못 골랐다는
뜻이니 그 자리에서 바로 알 수 있다.**

**⚠️ 반드시 CLI로 export한다 - 에디터 GUI의 "내보내기" 버튼은 쓰지
않는다.** 실제로 겪은 문제: `export_presets.cfg`를 이미 올바르게
고쳐뒀는데도(디스크 파일 자체는 정상 - `custom_features="yd_release"`가
그대로 있었음), 에디터를 열어 GUI로 export하니 `yd_release` 태그가 안
먹힌 빌드가 나온 적이 있다. 에디터가 파일을 열 때 시점에 따라 메모리에
든 프리셋 상태가 디스크와 어긋날 수 있고(이 세션에서 이미 프리셋
전체가 통째로 덮어써진 사고를 한 번 겪음 - 그보다 작은 규모로 필드
하나만 어긋나는 것도 같은 원인 계열이다), GUI로 export하면 그 어긋난
상태 그대로 빌드가 나온다. CLI(`--headless --export-release`)는 그
순간 파일을 새로 읽어서 export하므로 이런 어긋남 자체가 생기지 않는다 -
**베타/정식 배포처럼 정확성이 중요한 export는 항상 CLI만 쓴다.**
개발 중 화면을 눈으로 보는 `Web (dev)` export는 GUI로 해도 상관없다
(디버그가 켜진 채로 나오는 게 기본값이라 위험이 없음).

### 1. Render 무료 플랜에서 Godot 헤드리스 서버를 띄우는 방법

Render는 "Web Service"로 배포하는 게 기본 단위이고, 임의의 바이너리를
직접 올릴 수는 없다(빌드팩 또는 Docker 이미지 중 하나를 거쳐야 함) -
Godot 헤드리스 서버처럼 표준 런타임(Node/Python/...)이 아닌 바이너리는
**Docker 이미지 경로가 유일하게 안전한 선택**이다(빌드팩은 특정 언어
런타임을 전제하므로 Godot 바이너리를 다루기 까다롭다).

- **Dockerfile 구성 방향**: 베이스 이미지(예: `debian:bookworm-slim` 또는
  `ubuntu:22.04`, 헤드리스 실행에 GUI 종속성이 없어 가벼운 이미지로
  충분함)에 Godot 4.7.2 **headless/server export 템플릿**(에디터 전체가
  아니라 `Godot_v4.7.2-stable_linux.x86_64` 같은 헤드리스 바이너리, 또는
  export된 실행 파일 자체)을 올리는 두 가지 방식이 있다:
  - (A) 프로젝트 소스 + Godot 엔진 바이너리를 이미지에 같이 넣고
    컨테이너 시작 시 `godot --headless --path /app res://server_main.tscn`
    으로 실행. 엔진 바이너리를 매번 이미지에 포함해야 해서 이미지가
    커지지만, export 과정 없이 프로젝트 소스를 그대로 쓸 수 있어 로컬
    개발-배포 사이 불일치가 적다.
  - (B) `--headless --export-release "<서버용 프리셋>"`으로 **리눅스
    실행 파일을 미리 export**해서 그 실행 파일만 이미지에 담는다.
    이미지가 작아지지만, 서버 전용 export 프리셋을 새로 만들어야
    한다(지금 `export_presets.cfg`엔 `Web (dev)`/`Web (release)` 둘뿐이고
    둘 다 클라이언트용 - 서버는 애초에 `res://server_main.tscn`을
    `--path .`로 직접 돌리는 방식이라(위 "완료한 단계" 2-1/2-3 참고)
    지금까지 export를 거친 적이 없다).
  - **추천**: (A)로 시작 - 이미 검증된 실행 방식(`run_server.bat`과
    동일한 커맨드라인)을 그대로 컨테이너 안에서 재사용할 수 있어
    리스크가 적다. 이미지 크기는 무료 플랜에서 문제될 정도는 아니다.
- **포트 바인딩**: Render의 Web Service는 컨테이너가 **`$PORT`
  환경변수에 지정된 포트로 리슨**해야 인식한다(Render가 매번 랜덤하게
  또는 고정으로 할당 - 서비스 생성 시점에 정해짐). 아래 2번 항목이
  바로 이 부분에 대한 코드 변경 필요 사항이다.
- **빌드/실행 명령(Render 대시보드 또는 `render.yaml` 기준)**:
  - Build Command: Docker 이미지를 쓰면 Render가 `Dockerfile`을 보고
    자동으로 빌드하므로 별도 Build Command가 필요 없다(Dockerfile
    안의 `RUN`으로 처리).
  - Start Command: `godot --headless --path /app res://server_main.tscn`
    (포트는 CLI 인자로 안 주고 `$PORT` 환경변수를 코드가 직접 읽게 함 -
    아래 2번).
  - Render 무료 플랜은 아웃바운드 대역폭/실행 시간에 제한이 있으니
    실제 배포 전에 Render의 최신 무료 플랜 한도를 콘솔에서 다시 확인할
    것(문서 작성 시점 기준 수치는 바뀔 수 있음).

### 2. PORT 환경변수 처리 — **완료**

현재 `server_main.gd::_resolve_port()`는 CLI 인자 → `YACHT_DICE_PORT`
환경변수 → 기본값(8910) 순으로 포트를 정한다. **Render는 이 중 어느
것도 안 쓴다** - Render는 항상 자기가 정한 포트를 `PORT`라는 이름의
환경변수로 컨테이너에 주입하고, 서비스가 그 포트로 리슨하는지 감시해서
안 하면 배포를 실패로 처리한다. 즉 지금 코드 그대로 Render에 올리면
`YACHT_DICE_PORT`를 아무도 설정 안 해서 기본값 8910으로 계속 리슨하는데,
Render는 (Render가 실제로 트래픽을 연결해줄) `$PORT` 쪽을 아무도 안
듣고 있다고 판단해 서비스를 죽은 것으로 취급할 가능성이 크다.

**적용된 변경**: `_resolve_port()`의 우선순위를 "CLI 인자 →
`PORT`(Render 표준) → `YACHT_DICE_PORT`(우리 자체 로컬 개발용) →
기본값 8910"으로 조정했다(`server_main.gd`). `YACHT_DICE_PORT`는
로컬 개발/테스트에서 계속 쓰이므로(`port_override`로 우회하는 테스트
경로도 여전히 최우선으로 남음) 없애지 않고 `PORT`보다 낮은 우선순위로
남겨뒀다. 회귀 테스트(`test_server_port_resolution.gd`, 4건) -
`OS.set_environment()`로 실제 프로세스 환경변수를 조작해 4단계 우선순위
(아무것도 없음→기본값 / YACHT_DICE_PORT만/ PORT가 YACHT_DICE_PORT보다
우선 / port_override가 전부보다 우선)를 전부 확인했다.

**덤으로 확인 - 바인딩 주소**: `peer.create_server(port)`가
`bind_address` 인자를 안 넘겨서 Godot 기본값(`"*"`, 모든 인터페이스)을
쓴다 - Render의 "0.0.0.0에 바인딩해야 한다" 요구사항을 이미 만족하므로
별도 코드 변경 불필요.

### 3. 무료 플랜 유휴 대기(idle spin-down)와 방 정보 소실

Render 무료 플랜의 Web Service는 **일정 시간(문서 작성 시점 기준 약
15분) 요청이 없으면 인스�스를 완전히 내린다** - 다음 요청이 오면 그때
다시 컨테이너를 새로 띄우는데, 이 "깨어나는" 과정이 최대 1분 정도
걸릴 수 있다. 이건 이미 클라이언트 쪽 설계에 반영돼 있다
(`ReconnectBackoff` - 1,2,4,8,16초... 지수 백오프, 상한
`NetProtocol.MAX_RECONNECT_ATTEMPTS`, `docs/multiplayer.md` §6).

**핵심 문제**: 인스턴스가 내려가면 그 프로세스의 **메모리에만 있던
모든 방 상태(`RoomManager.rooms`)가 통째로 사라진다** - 디스크나
DB에 영속화하지 않으므로, 재시작된 새 컨테이너는 이전 방/토큰을 전혀
모른다. 이건 이미 §6에 "서버 재시작하면 재접속이 아니라
`ROOM_NOT_FOUND`로 조용히 끝나는 게 정상"이라고 문서화돼 있다 - 무료
플랜을 실제로 쓰면 이 경로가 **유휴 스핀다운 때마다 일상적으로**
발생한다는 점이 로컬 테스트와 다르다(로컬에선 사용자가 수동으로 서버를
끄기 전엔 절대 안 겪는 경로였음).

**"서버를 깨우는 중" 문구를 띄워야 할 조건 정리(사용자 요청)** - 이번
세션에 이미 `online_screen.gd::_connection_retry_label()`로 세 상황을
구분해뒀다(§6 "친구 대상 실제 베타 테스트 후속" 참고). Render 배포
후에는 이 세 조건의 **실제 발생 빈도**가 로컬과 크게 달라진다는 점만
새로 정리한다:
- **"서버를 깨우는 중입니다(최대 1분)"** - `_reconnecting_after_disconnect`도
  `_resuming_session`도 아닌 순수 첫 접속(`[방 만들기]`/`[방 참가]`를
  막 눌렀을 때). Render에서는 **이게 가장 흔한 경우**가 된다 - 무료
  플랜에서 유휴 스핀다운 후 첫 접속은 사실상 항상 이 상황이므로, 문구
  그대로("최대 1분") 정확하다.
- **"게임 도중 재접속 시도 중"** - 게임 화면에 이미 들어간 뒤 연결이
  끊겼을 때. Render에서는 스핀다운으로 서버가 사라지는 것도 이
  경로로 잡힐 수 있다는 게 로컬과 다른 점이다 - 재시도가 다 소진되면
  (`reconnect_exhausted`) 결국 `ROOM_NOT_FOUND`나 연결 실패로 끝나는데,
  이 경우 사용자에게 **"서버가 재시작되어 이전 게임 정보가 사라졌습니다"**
  같은 이유를 알려주는 게 지금의 일반적인 "재접속에 실패했습니다"보다
  낫다(아래 4번).
- **"이전 게임에 다시 연결하는 중"** - F5 등 세션 복귀 시도. Render
  에서는 유휴 스핀다운 뒤 며칠 지나 다시 켠 클라이언트가 이 경로를
  타는 경우, 서버가 그 방을 이미 잊어버린 상태(당연함)일 가능성이
  거의 100%다 - 이미 `_on_server_error()`의 세션 복귀 실패 처리
  (`SessionStore.clear()` + 연결 패널로 복귀)가 이 경우를 조용히
  넘어가도록 되어 있어(§6 - "혹시 몰라서 물어본 것") 별도 변경은
  필요 없어 보인다.

### 4. 서버가 죽거나 재시작될 때 클라이언트가 보여줘야 할 것

지금 클라이언트는 "방을 못 찾음"(`ROOM_NOT_FOUND`)과 "연결 자체가
안 됨"(`connection_failed`)을 서로 다른 경로/문구로 이미 구분하고
있지만(확인 2, `CLAUDE.md` "확인 1~4" 절 참고), **"서버가 재시작돼서
방이 사라졌다"는 사용자가 이해할 수 있는 형태로는 아직 설명되지
않는다** - `ROOM_NOT_FOUND` 에러 메시지(`_join_error_message()`,
`"그런 방을 찾을 수 없습니다."`)는 "방 코드를 잘못 입력했나?"와
"서버가 재시작돼서 없어졌나?"를 구분해주지 않는다. Render 배포
후에는 후자가 훨씬 흔해지므로, 재접속 시도 중(`_reconnecting_after_disconnect`)에
받은 `ROOM_NOT_FOUND`는 "서버가 다시 시작되어 이전 게임을 이어갈 수
없습니다 - 새로 방을 만들어 주세요" 같은 전용 문구로 갈라주는 걸
2-7 구현 시 검토한다(지금은 조사만 - 코드 변경 없음). 원칙:
- **조용히 멈추면 안 된다** - 이번 세션에 이미 하나 고쳤다(세션 복귀
  재시도 소진 시 화면이 멈춰 있던 버그, "확인 4" 참고) - Render로
  옮기면 이 경로를 훨씬 자주 타게 되므로 같은 종류의 "멈춤"이 또
  있는지 2-7 작업 시작 시 한 번 더 훑어야 한다.
- **엉뚱한 문구가 뜨면 안 된다** - "서버를 깨우는 중"이 실제로는
  "방금 배포가 재시작돼서 방이 영구히 사라졌다"를 가리키고 있는데
  똑같이 "곧 깨어날 것"처럼 보이면 사용자는 하염없이 기다리게 된다 -
  재시도가 소진된 뒤(`reconnect_exhausted`)의 안내 문구는 "다시
  시도해보세요"가 아니라 "새로 방을 만들어야 합니다"에 가깝게
  다듬을 필요가 있다.

### 5. Render 로그 확인 방법과 보관 기간

- Render 대시보드의 서비스 페이지 → **Logs** 탭에서 실시간 스트림을
  볼 수 있다(로컬의 콘솔 창을 보는 것과 비슷한 경험).
- **무료 플랜은 로그 보관 기간이 짧다**(문서 작성 시점 기준 며칠
  단위 - Render 쪽 정책이 바뀔 수 있으니 실제 배포 전 최신 한도를
  다시 확인할 것). 로컬에서는 `run_server.bat`이 `--log-file`로 파일에
  영구 보관하지만(이번 세션에 추가, 위 "확정 1~3" 참고), Render
  환경에서는 컨테이너 파일시스템도 재시작되면 같이 사라지므로 **로그
  파일을 컨테이너 안에 남기는 방식은 Render에서 의미가 없다** - 크래시가
  나면 그 순간 Render 대시보드의 로그를 바로 캡처해두거나, 필요하면
  외부 로그 수집 서비스(Render의 로그 스트림을 외부로 전달하는 기능,
  또는 별도 로깅 서비스 연동)를 검토해야 한다. 이건 2-7 구현 범위에
  포함해서 판단할 것 - 지금은 "무료 플랜 로그가 금방 사라진다"는 제약만
  기록해둔다.

### 6. 확정된 구현 계획 (사용자 검토·확정 - 이 순서로 진행)

**결정 1 - 크래시 게이트**: 양방향 팩 전송(양쪽 다 커스텀 캐릭터) 재현을
한 세션 한도로 한 번 더 시도한 뒤 진행한다(위 "전제" 참고). 크래시가 안
나오면 그대로 진행 - 무한정 붙잡지 않는다. **→ 완료, 크래시 안 남
(위 "전제" 갱신 내용 참고) - 그대로 진행한다.**

**결정 2 - 접속 주소는 빌드 종류로 자동 분기**: 배포 빌드(`yd_release`
기능 태그 있음, `build_info.gd`가 이미 구분함)는 기본 주소를 Render

팔로워/지인 등 불특정 다수에게 공개할 것이므로 주소를 직접 입력하게
두지 않는다. 수동 입력 필드는 없애지 않고 눈에 덜 띄는 위치로만
남긴다(로컬 테스트/장애 우회용). Render URL은 상수 한 곳에만 두고,
"바꾸면 클라이언트 재빌드 + GitHub Pages 재배포가 필요하다"고 주석에
남긴다.

**순서를 바꾼 이유 - 가장 위험한 미지수를 앞으로**: Render 무료 플랜에서
WebSocket 연결이 실제로 얼마나 유지되는지가 이 계획 전체의 성패를
가른다. Render 공식 문서는 고정 타임아웃이 없다고 하지만, 일부
커뮤니티 자료(예: 파이썬 `websockets` 라이브러리의 Render 배포 가이드)는
"무료 플랜은 5분 뒤에 연결이 끊긴다"고 적고 있다 - 요트다이스 한 판은
5분보다 길므로, 후자가 맞으면 무료 플랜으로는 서비스가 불가능하다.
**문서로 결론 내지 않고 실측한다** - 서버가 뜨자마자 클라이언트를 손대기
전에 브라우저 하나로 15분 이상 유지하며 30초 간격 로그(연결 유지
시간/접속 수)로 정확히 언제 끊기는지, 유휴 때문인지(주기적 메시지로
해결되는지) 확인한다. "5분에 끊기고 주기적 통신으로도 안 풀리면" 무료

## 7. 단계 5 — 첫 배포 결과: 후보 A 실패, 후보 C로 전환 (2026-09-17)

### 확인된 사실 (Render 배포 로그)

```
ERROR: Not enough response headers, got: 3, expected >= 4.
   at: _parse_client_request (modules/websocket/wsl_peer.cpp:162)
   [0] _process (res://server_main.gd:192)
==> No open HTTP ports detected on 0.0.0.0, continuing to scan...
```

### 해석

- **포트 자체는 정상적으로 열려 있었다** - Render의 포트 스캐너가 실제로
  TCP 접속에 성공했다. 위 `ERROR`는 그 접속에 대해 Godot의 WebSocket
  서버가 정식 WebSocket 핸드셰이크(헤더 4개 이상)를 기대했는데 평범한
  HTTP 요청(헤더 3개)이 와서 파싱에 실패하고 거부한 흔적이다 -
  **"포트가 안 열렸다"가 아니라 "열린 포트가 HTTP에 응답을 안 했다"는
  뜻**이다.
- **Render는 "포트가 열려 있음"이 아니라 "HTTP 요청에 응답함"을
  요구한다.** Render 공식 문서/커뮤니티 답변에 "Services running on
  Render must open an HTTP port"로 명시돼 있다 - 순수 TCP 개방만으로는
  부족하다.
- 서비스 상태는 "Deployed"로 표시됐지만, 위 로그로 볼 때 **외부 트래픽
  라우팅 자체가 성립하지 않았을 가능성이 높다**(포트 스캐너가 계속
  "continuing to scan..."을 반복하는 것은 아직도 감지를 못 했다는 뜻).

### 결론 - 후보 A는 실측으로 확정 실패했다

**후보 A(Health Check Path를 비워둔다)로는 해결되지 않는다.** 이전 판단
("Health Check Path를 비워두면 Render 기본값이 TCP 소켓 확인"이라는
공식 문서 내용)은 **틀리지 않았다** - 실제로 위 실패는 Health Check
Path 설정과 무관한, **그보다 앞선 "포트 감지" 단계 자체의 요구사항**
때문이다. 즉 헬스 체크를 아예 안 쓰기로 해도, Render가 서비스를
"떠 있다"고 인식하려면 그 포트가 최소한 평범한 HTTP 요청 하나엔
답해야 한다는 게 이번에 실측으로 확정된 사실이다. **이 판단은 앞으로
다시 검토하지 않는다** - 후보 A/B를 다시 시도해볼 이유가 없다(둘 다
"Godot이 HTTP에 안 답한다"는 같은 근본 제약을 못 피한다).

**→ 후보 C(컨테이너 안에 작은 HTTP 프록시를 두고, 그 프록시가 평범한
요청엔 직접 답하고 WebSocket 업그레이드 요청만 내부 Godot 서버로
넘기는 구조)로 전환한다.** 상세 설계는 바로 아래 절.

## 8. 후보 C 설계안 — 구현 + 로컬 검증 완료 (2026-09-17)

**사용자가 설계를 승인하고 5가지를 추가 지시**: nginx 프록시 타임아웃

설정(`proxy_http_version 1.1` + `Upgrade`/`Connection` 헤더), 기동
순서(Godot 준비 후 nginx 시작 + 상한 있는 대기), 헬스 응답 본문(사람이

/ (Upgrade 헤더 있음) 내부 고정 포트(8910)의 Godot 서버로 전달`.

### 로컬 검증 결과 (6단계 전부 통과, 포트는 외부 10000/내부 8910으로 분리)

`docker run -p 18910:10000 -e PORT=10000 ...`(Render가 실제로 주는 값에
가깝게 10000을 공개 포트로, Godot 내부 고정 포트 8910과 겹치지 않게 함).

1. 빌드 성공.
2. `docker logs`에 Godot 배너(`[YachtDice] 빌드: ...`)와 `[nginx]` 접두어
   로그 둘 다 확인됨.
3. `curl -i http://localhost:18910/` → `HTTP/1.1 200 OK`, 본문
   `yacht-dice server: ok` 확인.
4. 실제 `GameClient`를 임시 씬으로 띄워 `ws://127.0.0.1:18910`에 연결 -
   `hello_ack` 수신까지 확인(nginx를 거쳐 Godot까지 실제로 도달함).
5. **컨테이너 안에서 Godot 프로세스만 강제 종료(`kill -9`) → 컨테이너가
   즉시 종료 코드 137로 죽는 것 확인**(`docker inspect`로 재확인). 로그에
   `[entrypoint] Godot이 먼저 종료됨(코드 137) - nginx도 같이 내립니다`가
   정확히 찍혔다 - "프록시만 살아있고 게임 서버는 죽어있는" 최악의
   상태가 성립하지 않음을 실측으로 확인했다.
6. 컨테이너 정리 완료.

**막혔던 것 하나**: 이 이미지(`debian:bookworm-slim`)에는 `kill`/`pgrep`
바이너리가 따로 없다(procps 패키지 미설치) - `docker exec`로 직접
`kill`을 실행하면 "executable file not found"로 실패한다. `sh -c "kill
-9 <pid>"`처럼 셸을 거쳐야 셸 내장 `kill`이 동작한다(운영 목적의 변경은
아니고, 이번 로컬 검증 방법에만 해당하는 메모).

### 후속 - 첫 재배포에서 발견된 새 문제: Godot이 0.0.0.0에 그대로 바인딩돼 있었음

후보 C 배포 후 헬스 응답은 정상이었지만, Render 로그에
`==> Detected a new open port TCP:8910`와
`ERROR: Not enough response headers, got: 3, expected >= 4.`가 1초에
한 번씩 반복됐다 - **포트는 실제로 열려 있었고(Render 스캐너가 접속에
성공), Godot의 WebSocket 서버가 평범한 HTTP 요청을 핸드셰이크로
착각하고 거부한 흔적**이었다(후보 A 실패 때와 같은 종류의 증상,
다만 이번엔 nginx가 아니라 Godot의 **내부 전용이어야 할** 포트에서
발생). 원인은 Godot이 여전히 `create_server(port)`를 바인드 주소
인자 없이 불러 기본값 `"*"`(모든 인터페이스)로 열려 있었던 것 -
같은 컨테이너 안에서만 보이면 될 포트가 Render의 스캐너에도 그대로
보였다.

**왜 그냥 두면 안 되는가(세 가지)**: (1) 로그가 이 에러로 도배돼
`[서버][연결계측]`이 묻혀 단계 6 측정이 불가능해진다. (2) Render가
8910을 "새로 감지한 포트"로 인식했으므로, 외부 트래픽 라우팅 대상이
nginx가 아니라 Godot으로 바뀔 위험이 있다(그러면 지금 되던 게 갑자기
안 되기 시작하고 원인 추적이 어려워진다). (3) 무료 인스턴스에서 1초마다
에러를 처리하는 것 자체가 CPU 낭비다.

**수정**: `server_main.gd`에 `_resolve_bind_address()`를 포트와 같은
방식(CLI 인자 최우선)으로 추가하고, `peer.create_server(port,
bind_address)`로 바꿨다. 기본값은 `"*"`(로컬 개발 기존 동작 유지) -
`docker-entrypoint.sh`가 컨테이너 안에서만 두 번째 CLI 인자로
`"127.0.0.1"`을 명시적으로 넘긴다. 시작 로그에 실제 바인딩을 출력한다
(`[서버] 바인딩: 127.0.0.1:8910 (외부 노출 안 됨 - 컨테이너 내부 전용
등)`) - 예전처럼 어디에 붙었는지 안 보이면 같은 혼란이 재발한다.
**원칙: Godot은 항상 내부 전용(127.0.0.1)이고, 외부에 노출되는 것은
nginx뿐이다 - 이 값을 "*"로 되돌리면 Render 스캐너가 다시 찌른다.**

**로컬 검증(3가지, 전부 통과)**:
1. **내부 포트가 외부에서 안 열려 있는지** - Docker Desktop(Windows)은
   `-p`로 게시한 포트가 컨테이너 안의 `127.0.0.1` 바인딩까지 우회해서
   뚫어버리는 특성이 있어(userland 프록시 방식 - 네이티브 Linux Docker의
   iptables NAT와 다름) `-p`만으로는 이 검증이 안 된다는 것을 실제로
   확인했다. 대신 같은 브리지 네트워크의 **다른 컨테이너**(`curlimages/curl`)에서
   대상 컨테이너의 실제 IP로 직접 접속을 시도해 확인했다 -
   `172.17.0.2:8910`(Godot)은 연결 자체가 거부됨(curl exit 7,
   `HTTP:000`), 같은 IP의 `:10000`(nginx)은 정상적으로 200을 받음 -
   같은 조건에서 하나는 막히고 하나는 뚫리는 대조를 확인했으므로 이
   결과를 신뢰한다.
2. **nginx 경유 WebSocket이 Godot까지 도달하는지** - 실제 `GameClient`로
   `ws://127.0.0.1:18910`(nginx가 받는 게시 포트)에 연결해 `hello_ack`
   수신까지 재확인.
3. **평범한 HTTP 요청이 여전히 200인지** - `curl`로 재확인.
4. **기동 순서(Godot 준비 대기 → nginx 시작)가 127.0.0.1 바인딩에서도
   동작하는지** - `docker-entrypoint.sh`의 준비 확인 로직은 애초에
   `/dev/tcp/127.0.0.1/${INTERNAL_PORT}`로 127.0.0.1을 대상으로 하고
   있어서(0.0.0.0을 전제한 적이 없었음) 수정이 필요 없었다 - 컨테이너가
   정상적으로 "Godot 준비 완료 - nginx 시작" 순서로 뜨는 것으로 재확인.

새 테스트 2개(`test_server_port_resolution.gd`) - 바인드 주소 기본값
(`"*"`)과 override 우선순위 확인. 전체 913개 테스트 통과.

### 정정 - 127.0.0.1 바인딩은 원인 진단이 틀렸다(사용자 지적, 2026-09-17)

**가설(틀림)**: Render의 포트 스캐너가 컨테이너 **외부**에서 접근한다고
판단했다 - 그래서 Godot을 `127.0.0.1`로 바인딩하면 스캐너 눈에 안
보일 것이라고 결론 냈다.

**실제로 확인된 것**: 재배포(`6e4f88f`) 후에도 `_parse_client_request`
에러가 초당 1회 그대로 계속됐다 - `[서버] 바인딩: 127.0.0.1:8910`
로그는 정상 출력됐으므로(수정 자체는 적용됨), 바인딩 변경이 문제를
없애지 못한다는 뜻이다. **`Detected a new open port TCP:8910`이라는
Render 메시지가 우리 컨테이너의 로그 스트림에 그대로 섞여 나온다는
사실 자체가, 그 스캐너가 컨테이너 안쪽(같은 네트워크 네임스페이스)에서
동작한다는 증거다** - `127.0.0.1`은 "외부에서 안 보이게" 할 뿐 "같은
네임스페이스 안의 다른 프로세스에서 안 보이게" 하지는 못한다(정확히
`docker-entrypoint.sh`의 준비 확인 로직 자체가 `127.0.0.1:8910`에
접속해서 확인하는 것과 똑같은 방식으로, 컨테이너 내부의 어떤 프로세스든
그 포트에 닿을 수 있다).

**127.0.0.1 바인딩 수정 자체는 유지한다** - 외부 노출 표면을 줄이는
것은 스캐너 소음과 별개로 여전히 옳은 방향(원칙: Godot은 항상 내부
전용, 외부에 노출되는 것은 nginx뿐)이다. **다만 이것이 스캐너 소음을
없애지는 못한다는 점을 명확히 한다** - 소음의 원인은 바인딩 주소가
아니라 Render의 Docker 서비스 포트 자동 감지 방식(아래 "시도해볼 것"
참고) 쪽에 있는 것으로 보인다.

**로컬 검증의 한계**: 이 정정 자체를 로컬에서 재현/검증하기는
어렵다 - Docker Desktop(Windows)에는 애초에 Render의 포트 스캐너에
해당하는 것이 없고, 위 "로컬 검증(3가지)" 항목에서 이미 확인했듯
Docker Desktop의 `-p` 게시 포트는 `127.0.0.1` 바인딩을 오히려
우회해버리는 특성(userland 프록시)까지 있어서, "컨테이너 내부에서
동작하는 스캐너가 127.0.0.1 바인딩을 우회하는지" 같은 이번 시나리오는
로컬 Docker Desktop 환경 자체가 재현 대상과 다르다 - 이 부분은 실제
Render 배포 로그로만 확인 가능했다.

**판단(사용자, 고장이 아니라 소음)**: 헬스 응답/외부 주소/nginx 경유
전부 정상이라 서비스 자체는 동작한다. 실질적 피해는 로그가 에러로
도배돼 `[서버][연결계측]`이 묻히는 것과 초당 1회 에러 처리로 인한
미미한 CPU 낭비 둘뿐이다 - **이것 때문에 단계 6 측정을 미루지 않는다.**
로그 필터(`"연결계측"`)를 걸고 측정을 진행하기로 함 - 유의사항은 아래
"단계 6" 절의 "★ 로그 필터 사용 시 유의사항" 참고.

**시도해볼 것(사용자가 Render 대시보드에서 직접, 코드 변경 아님)**:
Render 커뮤니티의 에러 문구("failed to detect open port 5432 from PORT
environment variable")에 근거해, PORT 환경변수를 Environment 탭에
**명시적으로** 추가하면(예: `PORT=10000`) Render가 그 값을 기준으로만
판정하고 블라인드 스캔 자체를 안 할 가능성이 있다고 보고 시도하기로
했다. 컨테이너 쪽 영향 검토(구현 없이 분석만, 아래 표):

| 확인 항목 | 결과 |
|---|---|
| `docker-entrypoint.sh`가 `PORT=10000`을 받아 nginx에 정상 적용하는가 | **영향 없음** - `PORT="${PORT:-10000}"`은 이미 `PORT`가 비어있을 때만 기본값 10000을 쓰는 구조라, Render가 `PORT=10000`을 명시적으로 주입해도 결과값은 지금과 완전히 같은 10000이다(우연히 우리 기본값과 같은 숫자를 고르려는 것이 아니라, 이미 있던 기본값과 같은 값을 시도해보려는 것 - 결과적으로 동작 차이가 없다). 10000이 아닌 다른 값을 넣어도(8910만 아니면) 그대로 envsubst를 통해 nginx에 반영되므로 안전하다. |
| `PORT == 8910` 방어 코드가 오작동하지 않는가 | **영향 없음** - 비교 대상은 문자열 `"8910"`뿐이고 그 외 어떤 값이 와도 정상 통과한다. |
| 기동 순서/준비 대기 로직에 영향이 있는가 | **영향 없음** - 이 로직은 `INTERNAL_PORT`(8910, 고정)만 보고 `PORT` 값과 무관하다. |

**결론: 코드 수정 불필요.** Render 대시보드에서 `PORT` 환경변수를
추가/변경하는 것은 컨테이너 쪽에서 완전히 안전하다 - 사용자가 측정을
마친 뒤 시도해도 된다. **실제로 시도했으나 해결되지 않았다** - 아래
"로그 필터"로 대응한다.

### 후속 - Render 포트 스캐너 소음을 로그 필터로 처리 (구현 완료, 2026-09-17)

**왜 이 필터가 존재하는가(나중에 "왜 로그를 감추지?"라고 의심하지
않도록 경위를 남긴다)**: Render의 포트 스캐너는 컨테이너 **내부**(같은
네트워크 네임스페이스)에서 동작한다(위 "정정" 절에서 실측으로 확인됨).
Godot을 `127.0.0.1` 전용으로 바꿔서 **외부** 노출은 막았지만, 이
스캐너는 컨테이너 내부에서 도니 127.0.0.1도 여전히 그대로 접근할 수
있다 - 그래서 Godot의 내부 전용 포트(8910)에도 평범한 HTTP 프로브를
계속 보낸다. Godot의 WebSocket 서버는 이 요청을 WebSocket 핸드셰이크로
파싱하려다 헤더 개수가 모자라 실패하고, 초당 1회 꼴로 4줄짜리 에러를
찍는다:

```
ERROR: Not enough response headers, got: 3, expected >= 4.
   at: _parse_client_request (modules/websocket/wsl_peer.cpp:162)
   GDScript backtrace (most recent call first):
       [0] _process (res://server_main.gd:213)
```

Environment 탭에 `PORT=10000`을 명시해봤지만 해결되지 않았다(스캐너의
블라인드 스캔 자체를 막지는 못하는 것으로 보인다). 서비스 동작
자체엔 무해하지만(헬스 응답/외부 접속/nginx 경유 전부 정상 - 위
"정정" 절 참고) Render Logs가 이 소음으로 도배돼 `[서버][연결계측]`이나
Phase 3의 친구 테스트 관찰 로그를 전혀 읽을 수 없게 만든다.

**구현**: `docker-log-filter.sh`(신규) - Godot의 표준출력/표준에러만
거른다(nginx 로그는 안 건드림). `docker-entrypoint.sh`가 Godot을
FIFO로 리다이렉트하고 이 필터가 그 FIFO를 읽어서 실제 컨테이너
로그로 내보낸다(FIFO를 쓰는 이유: 파이프로 바로 연결하면 `$!`가
필터의 PID가 되어버려 Godot 자신의 PID를 못 얻고, 그러면 준비 대기/
동반 종료 로직이 깨진다).

- **원칙 1(대상을 좁힘)**: `"ERROR: Not enough response headers"`로
  시작하는 줄만 블록의 시작으로 인식한다. 그 외의 모든 `ERROR:` 줄은
  손대지 않고 그대로 통과시킨다.
- **원칙 2(블록 단위 제거)**: 블록 시작을 인식하면 뒤따르는
  `   at: `/`   GDScript backtrace`/`       [N] ` 형태의 줄들(스택
  트레이스)도 같이 억제하다가, 이 패턴에 안 맞는 첫 줄을 만나는 즉시
  억제를 멈추고 그 줄부터 정상 출력으로 돌아간다.
- **원칙 3/4(조용히 안 지움 + 이상 신호 감지 가능)**: 5분마다
  `[필터] 포트 스캐너 프로브 에러 N건 억제됨 (최근 5분)`을 반드시
  찍는다 - **N이 0이어도 찍는다**(스캐너가 조용해지거나 갑자기 폭증하는
  것 자체가 신호이므로, "0이면 안 찍는" 로직을 안 씀).
- **원칙 5(끌 수 있게)**: 컨테이너 환경변수 `DISABLE_PORT_SCANNER_FILTER=1`로
  필터를 완전히 끌 수 있다 - 켜지면 필터는 순수 통과(`cat`)로 동작하고,
  꺼졌다는 사실 자체를 로그 첫 줄에 남긴다. 이 에러 자체를 다시
  조사해야 할 때 원본을 그대로 봐야 하므로 넣었다.
- 필터가 죽으면(버그 등) Godot이 FIFO에 쓰다가 버퍼가 차서 결국
  멈춘다 - `docker-entrypoint.sh`의 동반 종료 로직에 필터 프로세스도
  포함시켜서, 필터가 죽어도 Godot/nginx와 똑같이 전체가 같이 내려가게
  했다(기존 "둘 중 하나 죽으면 전부 죽는다" 원칙을 셋으로 확장).

**로컬 검증(요청받은 3가지 전부 확인)**:
1. **필터가 실제로 걸러내는지** - 컨테이너 안에서(같은 네임스페이스,
   Render 스캐너와 같은 위치) 내부 포트(127.0.0.1:8910)로 평범한
   HTTP 요청을 직접 보내 실제로 저 에러를 발생시켰다 - 필터가 켜진
   컨테이너의 로그엔 안 나타났다. **대조 확인**: 같은 요청을 이번엔
   `DISABLE_PORT_SCANNER_FILTER=1`로 띄운 컨테이너에 똑같이 보내니
   에러가 실제로(정확히 이 형태로) 찍히는 것을 확인했다 - "애초에 에러가
   안 났다"가 아니라 "필터가 실제로 지웠다"는 것을 이렇게 대조로
   증명했다.
2. **다른 종류의 ERROR는 통과하는지(대조군)** - 필터 스크립트에
   `"Not enough response headers"`로 시작하는 블록 하나와 완전히
   다른 내용의 가짜 `ERROR:` 블록을 같이 흘려보내서, 전자만 지워지고
   후자는 스택 트레이스까지 전부 그대로 통과하는 것을 확인했다.
3. **억제 건수 요약이 실제로 찍히는지** - 테스트용으로 주기를 줄인
   사본으로 5건 억제 후 정확히 "5건 억제됨"이, 억제가 없던 구간엔
   "0건 억제됨"이 찍히는 것을 확인했다(실제 배포본의 주기는 5분
   그대로 - 테스트 사본에서만 줄임).

추가로 필터 도입 후에도 회귀가 없는지: 평범한 HTTP 요청은 여전히
200을 받고, 실제 `GameClient`로 nginx 경유 WebSocket도 여전히
`hello_ack`까지 정상 도달하며, Godot 프로세스만 죽였을 때 컨테이너
전체(로그 필터 포함)가 여전히 종료 코드 137로 같이 내려가는 것까지
재확인했다.

### 1. 프록시 선택 - nginx 추천

| 후보 | 이미지 크기 영향 | 설정 복잡도 | 비고 |
|---|---|---|---|
| **nginx**(추천) | 작음 - 이미 `debian:bookworm-slim` 기반이라 `apt-get install nginx`로 몇 MB 추가(이미지가 이미 200MB대라 무시할 수준) | `map $http_upgrade`/`if ($http_upgrade...)` 한 번이면 끝 - 이 정확한 패턴(WS 업그레이드 판별 후 분기)이 nginx 공식 문서에 예시로 나올 만큼 표준적 | 가장 많이 검증된 조합, 실패 사례/해결법이 이미 잘 알려져 있음 |
| Caddy | nginx와 비슷하거나 약간 작음(단일 정적 바이너리) | `reverse_proxy`가 Upgrade 헤더를 자동 감지해서 설정이 더 짧을 수 있음 | 이 프로젝트에서 한 번도 안 써본 도구라 이번이 첫 검증 대상이 됨 - 익숙한 nginx 쪽이 위험이 적음 |
| 직접 짠 미니 프록시(Go/Python 등) | 가장 작을 수 있음 | **가장 높음** - HTTP/WS 핸드셰이크 파싱을 직접 구현/유지해야 함 | 후보 B(Godot 자체가 HTTP도 답하게)를 기각했던 이유("미니 HTTP 서버 재구현 비용")가 그대로 적용됨 - 여기서도 기각 |

**추천: nginx.** 표준적이고 검증된 방식이며, 이 프로젝트가 이미 "직접
파싱하는 미니 서버"를 후보 B에서 기각한 논리와 일관된다.

### 2. 내부 포트 처리 - 사용자 추정이 맞음

지금 `_resolve_port()` 우선순위는 "CLI 인자 → `PORT` → `YACHT_DICE_PORT`
→ 8910"이다. 컨테이너 안에는 Render가 넣어준 `PORT`가 항상 있으므로,
Godot을 인자 없이 그냥 실행하면 `PORT`(= nginx가 공개용으로 쓸 값과
같은 값)를 그대로 잡아버려 nginx와 포트가 충돌한다. **CLI 인자가
최우선이므로, 컨테이너 시작 스크립트가 Godot을 실행할 때 내부 고정
포트를 명시적으로 넘겨야 한다**(`-- 8910`) - `PORT` 환경변수는 여전히
컨테이너 안에 존재하지만 CLI 인자가 그보다 우선이라 무시된다. 코드
변경은 필요 없다 - 지금 우선순위 그대로 활용하면 된다.

`nginx.conf`는 반대로 `PORT`를 **읽어야** 하는데, nginx는 설정 파일에서
환경변수를 직접 못 읽는다(공식 nginx Docker 이미지가 쓰는 방식대로)
`envsubst`로 컨테이너 시작 시점에 템플릿을 실제 설정 파일로 치환해야
한다 - `gettext-base` 패키지(`envsubst` 제공, 아주 작음)를 추가 설치.

### 3. 프로세스 동반 종료 (가장 중요, 사용자 지적)

컨테이너의 시작 프로세스(entrypoint)를 얇은 bash 스크립트로 만들고,
Godot과 nginx를 둘 다 백그라운드로 띄운 뒤 **둘 중 하나가 먼저
끝나는 순간**(`wait -n`, bash 4.3+ 기능 - bookworm의 bash 5.2는 지원)
**나머지 하나를 강제 종료하고, 먼저 죽은 프로세스의 종료 코드를 그대로
컨테이너 종료 코드로 넘긴다.** 이러면 "프록시만 살아있고 게임 서버는
죽어있는" 상태가 구조적으로 성립할 수 없다 - Godot이 죽으면 즉시
nginx도 죽고, 컨테이너 자체가 죽은 것으로 Render에 보인다(Render가
크래시한 서비스를 재시작하는 정책에 그대로 올라탄다). SIGTERM도
잡아서 두 프로세스에 전달해야 한다(Render가 재배포/스케일 조정 시
컨테이너에 SIGTERM을 보내는데, 잡지 않으면 자식 프로세스들이 안 끝난
채로 강제 종료(SIGKILL)당할 수 있다 - "PID 1 문제").

의사코드:
```bash
#!/bin/bash
envsubst '${PORT}' < /etc/nginx/nginx.conf.template > /etc/nginx/nginx.conf

godot --headless --path /app res://server_main.tscn -- 8910 &
GODOT_PID=$!
nginx -g "daemon off;" &
NGINX_PID=$!

trap 'kill -TERM $GODOT_PID $NGINX_PID 2>/dev/null; wait; exit 0' TERM INT

wait -n
EXIT_CODE=$?
# 어느 쪽이 먼저 죽었는지 로그로 남기고(kill -0으로 생존 여부 확인),
# 나머지 하나도 반드시 같이 내린다.
kill -TERM $GODOT_PID $NGINX_PID 2>/dev/null
wait
exit $EXIT_CODE
```

### 4. 로그 구분

Docker는 컨테이너의 시작 프로세스(위 bash 스크립트)의 stdout/stderr만
캡처한다 - 스크립트가 Godot/nginx를 리다이렉트 없이 `&`로만 띄우면
둘 다 부모의 stdout/stderr를 그대로 물려받아 **같은 로그 스트림에
합쳐진다**(별도 조치 없이 자동으로 4번 요구사항의 절반은 충족됨).
**주의할 함정 하나**: nginx는 기본값이 로그를 **파일**(`/var/log/nginx/*.log`)에
쓰지 stdout이 아니다 - 이대로 두면 nginx 로그가 Render Logs 탭에
아예 안 보인다(조용히 사라지는 로그 - 이 프로젝트가 계속 경계해온
"계기가 거짓말하는" 패턴 그대로). `nginx.conf`에서 `access_log`/`error_log`를
`/dev/stdout`/`/dev/stderr`로 명시해야 한다. 두 프로세스를 구분하려면
nginx 쪽 `log_format`에 `[nginx]` 접두어를 넣는다 - Godot 쪽은 이미
`[YachtDice]`/`[서버]`/`[서버][연결계측]` 접두어가 있어 구분할 필요가
없다. (참고: 두 프로세스가 같은 스트림에 동시에 짧은 줄을 써도 리눅스
파이프는 4KB 이하 쓰기를 원자적으로 보장하므로 로그 한 줄 안에서
글자가 섞이는 걱정은 안 해도 된다.)

### 5. 로컬 Docker 검증 계획 (Render에 올리기 전에 여기서 전부 확인)

1. `docker build`로 이미지 빌드.
2. `docker run -d --name yacht-c-test -p 18910:8910 -e PORT=8910 yacht-dice-server:latest`
   (호스트 포트를 nginx가 듣는 포트에 매핑 - Render 환경과 동일하게
   `PORT` 하나로 nginx/Godot 둘 다 맞춰 돌아가는지 확인).
3. `docker logs yacht-c-test`로 Godot 배너(`[YachtDice] 빌드: ...`)와
   nginx 로그(`[nginx] ...`)가 **둘 다** 찍히는지 확인(4번 요구사항).
4. 평범한 HTTP 요청 확인: `curl -i http://localhost:18910/` (또는
   PowerShell `Invoke-WebRequest`) → `200`이 와야 한다.
5. WebSocket이 Godot까지 도달하는지 확인: 이번 세션에서 이미 만든
   방식(실제 `GameClient`를 임시 씬으로 띄워 `ws://localhost:18910/`에
   연결) 또는 Python `websockets` 라이브러리로 `hello`/`hello_ack`
   핸드셰이크가 실제로 오가는지 확인 - **nginx가 단독으로 200을 준
   것과 실제로 Godot까지 뚫린 것은 다른 확인**이므로 반드시 둘 다 본다.
6. 프로세스 동반 종료 확인(3번 요구사항의 실측): 컨테이너 안에서 Godot
   프로세스만 강제 종료(`docker exec yacht-c-test pkill -9 godot` 등) →
   `docker wait yacht-c-test`로 컨테이너 자체가 종료되는지, `docker
   inspect --format='{{.State.ExitCode}}' yacht-c-test`로 종료 코드가
   0이 아닌지 확인.
7. 확인 후 `docker rm -f yacht-c-test`로 정리.

**여기서 6번까지 전부 통과해야 Render에 올린다** - 특히 6번은 로컬에서
반드시 끝내야 할 항목이다(Render에 올린 뒤에 이걸 재현하려면 대시보드를
뒤져야 해서 훨씬 비싸다).

## 9. 단계 6 — 연결 유지 시간 실측 계획 (이 계획 전체의 go/no-go 분기점)

### ★ 전제 조건 - 측정 시작 전에 반드시 확인할 것

**`nginx.conf.template`의 `proxy_read_timeout`/`proxy_send_timeout`이
`3600s`로 되어 있는지 먼저 확인한다.** nginx의 기본값(60초)을 그대로
두고 측정하면, 60초 넘게 무통신이면 **nginx가 스스로 연결을 끊는다** -
이걸 그대로 두고 측정하면 "Render가 몇 분 만에 끊었다"고 착각하지만
실제로는 nginx가 끊은 것이다(우리 5초 ping이 있으니 정상 상황에선 이
타임아웃에 안 걸려야 맞지만, 값 자체가 낮게 남아있으면 언제든 이
착각이 재발할 수 있다). 후보 C 도입 이후 이 값이 실수로 지워지거나
줄어들지 않았는지가 이 실측 전체의 신뢰도를 좌우한다.

### ★ 로그 필터 사용 시 유의사항 (Render 스캐너 소음 우회용)

Godot의 0.0.0.0/127.0.0.1 바인딩과 무관하게 Render의 내부 포트 스캐너가
`_parse_client_request` 에러를 초당 1회 남기는 소음이 있다(위 "정정"
절 참고 - 해결 안 됨, 다만 서비스 동작에는 지장 없음으로 판단됨).
측정 중 이 소음에 `[서버][연결계측]`이 묻히지 않도록 Render Logs 탭에
`"연결계측"` 문자열로 필터를 걸고 진행한다.

**주의**: 이 필터를 걸어두면 `[YachtDice] 빌드: ...` 시작 배너도 같이
걸러진다 - 배너는 "연결계측"이라는 문자열을 포함하지 않기 때문이다.
그런데 이 배너가 다시 찍히는 것이야말로 "인스턴스가 재시작(스핀다운→
재기동)했다"는 유일한 확실한 신호다(위 "인스턴스 스핀다운과 연결만
끊김을 구분하는 법" 참고) - **필터를 켠 채로만 측정하면 스핀다운이
일어났는데도 놓칠 수 있다.** 그러므로 측정을 마친 뒤에는 반드시 필터를
풀고, 측정했던 시간대 전체를 다시 훑어 그 사이 배너가 다시 찍힌
적이 있는지 확인한다 - 없었다면 인스턴스가 한 번도 재시작 안 된
것이고, 있었다면 그 시점에 유휴 스핀다운(또는 다른 이유의 재시작)이
있었다는 뜻이다.

### 배경 - Render 공식 문서로 확인된 것 (2026-09-17)

- **무료 플랜은 15분 동안 "인바운드 트래픽이 전혀 없으면" 인스턴스를
  스핀다운한다** - 공식 문서 원문: "spins down after 15 minutes without
  receiving any inbound traffic". 스핀업은 다음 요청이 올 때 자동으로
  일어나고 약 1분 걸린다.
- **"인바운드 트래픽"에는 새 연결만이 아니라 이미 열려 있는 WebSocket
  연결 위의 메시지도 포함된다** - 공식 문서 원문: "both HTTP requests
  and WebSocket messages from existing connections"로 명시돼 있다.
  즉 **우리 서버가 5초마다 보내는 ping과 클라이언트의 pong 응답도
  "인바운드 트래픽"으로 잡혀서 유휴 스핀다운을 막을 것으로 예상된다** -
  이게 사용자가 지적한 "유리한 사실"의 근거다.
- **Render는 WebSocket 연결 자체에 별도의 고정 최대 시간을 두지 않는다** -
  공식 문서/커뮤니티 답변 모두 "연결 시간 자체의 상한은 없다"는 쪽으로
  일관됨. 연결이 끊긴다면 이유는 위 유휴 스핀다운이거나, 배포/플랫폼
  점검으로 인스턴스가 교체되는 경우(예측 불가, 우리가 막을 수 없음)다.
- **이전에 다른 자료(파이썬 `websockets` 라이브러리 가이드 등)가 언급한
  "5분" 같은 수치는 위 공식 문서와 안 맞는다** - 어느 쪽이 실제 우리
  환경에서 맞는지는 문서로 결론 내지 않고 아래 실측으로 확인한다(사용자
  방침).

### "끊김"과 "인스턴스 정지"를 구분하는 법 (사용자 요청)

Render 대시보드에서 볼 수 있는 두 가지는 서로 다른 사건이다 - 헷갈리지
않으려면 이 둘을 분리해서 봐야 한다:

- **인스턴스 스핀다운(정상 - 유휴 15분)**: Render 대시보드의 **Events
  탭**에 "Instance stopped due to inactivity" 계열 이벤트가 뜬다.
  **우리 애플리케이션 로그(Logs 탭)는 이 시점에 새로 안 찍힌다** - 인스턴스
  자체가 멈췄으니 당연히 우리 `print()`도 안 나온다. 다음 요청이 오면
  Events 탭에 재기동 이벤트가 뜨고, Logs 탭에 우리 서버의 시작 배너
  (`[YachtDice] 빌드: ...`)부터 다시 처음부터 찍힌다 - **"서버가 처음부터
  다시 시작했다"는 로그 자체가 스핀다운·재기동이 있었다는 확실한 증거다.**
- **WebSocket 연결만 끊김(우리 코드 문제 또는 네트워크 순단)**: 인스턴스는
  안 멈췄으므로 Logs 탭에 우리 서버 로그(`[연결계측]` 주기 로그 등)가
  **끊김 없이 계속 찍힌다.** 그 와중에 `_on_peer_disconnected()`의
  "연결 해제: peer N, 총 유지 M초, 사유=..." 한 줄만 나타나고, 서버
  프로세스 자체(배너/시작 로그)는 다시 안 찍힌다.
- **판별 요령 한 줄**: **서버 시작 배너(`[YachtDice] 빌드: ...`)가 로그에
  또 찍히면 인스턴스가 재시작된 것(스핀다운→재기동)이고, 안 찍히고
  "연결 해제"만 있으면 그냥 그 연결 하나만 끊긴 것이다.**

### 정정 - "배너 재출현 없음" 판단이 틀렸다 (2026-09-17)

**틀렸던 판단**: 처음엔 "22분 측정 구간에 `[YachtDice]` 배너 재출현 없음 →
인스턴스 재시작 없음, 유휴 정지 없음"이라고 결론 냈다.

**실제로 확인된 것**: Render 로그의 실제 배너 출현 시각(Sep 17)은
아래와 같았고, 이 중 둘은 측정 구간(20:30:10~20:52:12) **안에** 있다.

| 시각 | 인스턴스 식별자 |
|---|---|
| 08:06:55 | `7bv6g` |
| 08:42:37 | `8cbbb` |
| 08:50:45 | `2rsdr` |
| 08:58:39 | `trs6x` |
| 08:59:21 | `2zkbx` |

판단이 틀렸던 이유: 근거로 삼은 로그가 `"연결계측"`으로 **필터된**
것이었다 - 필터를 걸면 배너 줄이 안 보인다는 걸 위에서 직접 경고해놓고,
정작 결론을 낼 때 그 사실을 놓쳤다.

**그래도 "22분 유지"라는 결론 자체는 유효하다** - 다만 근거를 바꾼다.
"배너가 없었다"가 아니라 **"측정 구간 내내 연결이 끊기지 않았으므로,
그 연결을 담당하던 인스턴스는 22분 동안 재시작하지 않았다"**가 근거다
(인스턴스가 재시작됐다면 그 인스턴스가 들고 있던 WebSocket 연결도
같이 끊겼을 것이다 - 5개 배너의 인스턴스 식별자가 전부 다르다는 것도,
위 배너들이 측정 대상 연결과 무관한 다른 인스턴스(같은 날 여러 차례
있었던 배포로 새로 뜬 것들)의 것이라는 해석을 뒷받침한다).

**"유휴 정지 없음"은 근거가 사라졌으므로 격하한다: 확인되지 않음.**
배너가 (재시작이 아니라) 배포 때문이었다면, 오늘 인스턴스가 유휴로
잠들었다가 다시 깨어난 적이 있는지는 이 로그만으로는 알 수 없다.

**교훈**: **필터를 건 로그로 "무엇이 없었다"를 주장하지 마라.** "없다"는
결론은 필터를 푼 전체 로그를 실제로 다 봤을 때만 낼 수 있다 - 필터는
"있는 것 중 관심 있는 것만 보기"에는 안전하지만, "없다는 걸 확인하기"에는
정반대로 위험하다(관심 밖으로 걸러진 바로 그 항목이 없다는 증거가 될 수
있어서).

### 무효 측정(1차·2차) - 원인과 교훈

**1차 측정이 무효였던 이유**: 방을 만든 뒤 Render 로그를 확인하려고
**같은 브라우저의 다른 탭으로 전환**했다 - 이 순간 게임 탭이 비가시
상태가 되어 Godot 웹 빌드의 메인 루프(`requestAnimationFrame` 기반)가
멈췄다. 핑도 안 나갔고, 서버가 15초 뒤 정상적으로 "핑 무응답"으로
연결을 끊었다 - **Render가 끊은 게 아니라 우리 서버가 끊은 것**이었다
(자세한 조사는 `docs/multiplayer.md` §12).

**2차 측정도 무효였던 이유**: 로그를 보기 위해 별도 창을 새로 열었는데,
그 과정에서 게임 창이 가려지거나 포커스를 잃어 1차와 같은 함정을
다시 밟았다(비가시화 조건은 "다른 탭 전환"뿐 아니라 "창 자체가
최소화/완전히 가려짐"에서도 성립할 수 있음 - `docs/multiplayer.md` §12
참고).

**교훈(★ 다음에도 반드시 기억할 것)**: **관찰하려는 행위 자체가 측정
대상을 바꿨다.** 로그를 실시간으로 보려고 창을 전환하는 순간 게임이
멈춘다 - 이건 이 프로젝트가 반복해서 겪어온 "계기가 거짓말한다"는
패턴의 새로운 변종이다(계기 자체는 정직했다 - 핑 무응답 15초는 사실
그대로다. 다만 **측정자가 관찰 방법으로 측정 대상의 환경 조건 자체를
바꿔버렸다**). **측정 중에는 아무것도 보지 말고, 끝난 뒤 로그 기록을
읽어야 한다** - 3차 측정(성공)은 두 창을 미리 나란히 배치해두고 측정이
끝날 때까지 어느 쪽도 조작/전환하지 않는 방식으로 이 함정을 피했다.

| 서버 로그의 "사유" | 실제 의미 | 원인 |

분류한 뒤 대응(재현 시도/보고/무시)을 결정한다.

데 쓴다.

**기록할 항목**:
1. 유휴 방치 시작 시각, 그 순간까지의 마지막 로그 줄.
2. **유휴 정지가 실제로 언제 일어났는지** - Events 탭에 스핀다운
   이벤트가 뜨는 시각을 기록(20분 이상 방치 예정 - 문서상 15분 유휴
   기준이므로 그 사이 어딘가에서 일어나야 정상).
3. 재접속 시도(첫 접속) 시작 시각.
4. **실제로 연결이 붙는 순간까지 걸린 시간**(초) - 이게 이번 측정의
   핵심 숫자.
5. 그 접속 성공 시점에 `[YachtDice]` 배너가 Logs 탭에 새로 찍히는지
   (찍혀야 정상 - 안 찍히면 "그 인스턴스가 사실 안 죽어 있었다"는
   뜻이라 유휴 정지 자체가 예상대로 안 됐다는 신호).
6. (참고용) 클라이언트 화면에 뜨는 "서버를 깨우는 중입니다(최대 1분)"
   문구가 실제로 몇 초까지 버티다 포기하는지, 포기했다면 그 시점의
   `_reconnect_backoff.attempt` 값에 해당하는 재시도 횟수도 같이 적으면
   아래 "클라이언트 재시도 예산" 계산과 바로 대조할 수 있다.

**클라이언트의 접속 재시도 예산 - 구현 완료 (2026-09-17)**

**근거를 실측 없는 추정이 아니라 Render 공식 안내로 바꿨다.** Render
공식 문서 원문:

> "Your free instance will spin down with inactivity, which can delay
> requests by 50 seconds or more."

즉 유휴 정지가 실제로 일어나고, 그 뒤 첫 요청은 50초 이상 걸릴 수
있다는 게 Render 스스로 밝힌 사실이다 - 예전 백오프 합(31초)으로는
잠든 서버에 거의 확실히 재시도를 다 쓰고 포기했을 것이다.

- `scripts/net/game_client.gd`에 `CONNECT_TIMEOUT_SEC`(10초)를
  추가했다 - 연결 시도가 `CONNECTING`/`AWAITING_HELLO_ACK` 상태에서
  이 시간을 넘기면 직접 실패로 판정하고 로그를 남긴다("연결 시도
  포기(N초 경과, 상한 10초)"). 이 값은 "한 시도가 무한정 안 끝나는
  것"만 막는 안전장치다.
- **실측으로 정정한 것 하나**: 처음엔 "이 10초 × 시도 횟수"를 백오프
  합에 더해서 총 예산을 계산했는데, 실제로 도달 불가능한 주소로
  재현해보니 **연결 시도가 이 10초를 다 못 채우고 훨씬 빨리(약 3초
  만에) 실패하는 경우가 있었다** - 그러면 이 타임아웃 자체가 안
  걸리므로 총 대기 시간을 못 늘려준다. 그래서 **총 예산을 안정적으로
  보장하는 건 각 시도의 소요 시간이 아니라 백오프 합 자체**라는
  결론을 냈다.
- `scripts/net/protocol.gd`의 `NetProtocol.MAX_RECONNECT_ATTEMPTS`를
  5 → **9**로 늘렸다 - 백오프(1, 2, 4, 8, 16, 16, 16, 16, 16초, 4번째
  이후 상한 16초에서 고정)만 더해도 **95초**가 보장된다(각 시도가
  얼마나 빨리/느리게 실패하는지와 무관하게 항상 성립) - Render의
  "50초 이상"에 충분한 여유를 더한 값.
- **실측 검증**: 도달 불가능한 주소로 실제 재현 - 예전 값(5회)으로는
  약 49초 만에 재시도를 전부 소진하고 포기했다(50초에서 딱 1초
  모자람 - 실측으로 직접 확인, Render 실환경이었다면 딱 여기서
  실패했을 것이다). 새 값(9회)으로는 60초 시점까지도 계속 재시도
  중임을 재확인했다(1/9, 2/9, 3/9... 진행 중, 포기 안 함).
- 온라인 화면의 "서버를 깨우는 중입니다(최대 1분)" 문구는 사용자
  결정대로 **그대로 유지한다** - 다만 실제 동작(1분이 지나도 포기하지
  않고 계속 재시도)은 위 실측대로 보장된다. 재시도 카운터("재시도
  N/9, X초 후")가 1분이 지난 뒤에도 계속 갱신되며 화면에 남아있으므로,
  정적인 "(최대 1분)" 문구만 보고 오해할 위험은 낮다고 판단했다.
- 관련 회귀 하나도 같이 고쳤다: `GameClient._reset()`이 재시도마다
  `_ever_hello_acknowledged`(이전 이름 `_ever_connected`)를 매번
  지우고 있어서, "게임 도중 재접속을 시도하다 그 재시도 자체가 또
  실패"하는 흔한 경우에 엉뚱한 신호(`connection_failed`)로 빠질 뻔했다 -
  이제 이 값은 세션 전체에서 hello_ack를 한 번이라도 받았는지를
  정확히 추적한다.
- 새 테스트 4개(총 9개 확인), 전체 922개 테스트 통과. 실제 서버로
  정상 연결 시나리오도 재확인 - 회귀 없음.

### 운영 요령 - 베타 세션 시작 전 서버 미리 깨우기 (docs + 베타 안내에 반영)

**베타 세션을 열기 직전에 주최자가 먼저 서버 주소를 브라우저로 한 번
열어 깨워두면, 참가자들이 50초 이상을 기다리지 않는다.** 이 절차를
베타 진행 순서의 맨 앞에 넣는다 - 첫인상이 "링크를 눌렀는데 1분 가까이
아무 일도 없음"이 되는 것을 막는 가장 싼 방법이다.

**베타 시작 전 체크리스트(맨 앞에 추가)**:
1. `https://yacht-dice-server-4wqa.onrender.com`을 브라우저로 열어본다.
2. `yacht-dice server: ok` 응답이 오는지 확인한다(응답이 오기까지
   50초 이상 걸릴 수 있다 - 이건 정상이다, 바로 이걸 미리 겪어두는
   게 목적).
3. 확인되면 참가자들에게 게임 링크를 공유한다 - 이제 인스턴스가
   깨어있는 상태라 참가자들은 지연 없이 붙는다.
4. **주의**: Render 무료 플랜은 15분 무트래픽이면 다시 잠든다(§9 배경
   참고) - 링크 공유와 실제 플레이 시작 사이가 15분을 넘지 않게 한다.

### 탭 비가시화 안내 구현 범위 (제안 - 승인 후 착수)

**최소 범위로 제안한다(사용자 요청 - "과하게 만들지 마라")**: 새 JS
브릿지/`visibilitychange` 이벤트 연결은 **안 한다.** 이유: 탭이
숨겨지는 "동안"에는 어차피 아무 GDScript 코드도 못 돌아서 그 순간
뭔가를 보여줄 수 없고(§12에서 확인한 대로 메인 루프 자체가 멈춤),
탭이 "숨겨지기 직전"에 미리 경고하는 것도 실효성이 낮다(그 경고를
보자마자 탭을 넘겨버리면 의미가 없음). **사용자가 실제로 알아야 할
단 하나의 순간은 "돌아왔을 때"뿐**이고, 그 순간은 이미 존재하는
`game_reconnected` 신호로 정확히 포착된다 - 원인이 탭 비가시화든
진짜 네트워크 순단이든 상관없이, "끊겼다가 복구됐다"는 사실 자체가
사용자가 알아야 할 전부다.

**제안하는 변경(딱 한 곳)**: `Main.gd::_on_game_reconnected()`가
지금은 `reconnect_overlay.visible = false`로 배너를 즉시 조용히
숨기는데, 이걸 "연결이 끊겼다가 복구되었습니다" 문구를 잠깐(예:
3초) 보여준 뒤에 숨기도록 바꾼다 - 기존 `reconnect_overlay`/
`reconnect_status_label`을 그대로 재사용(새 UI 노드 없음), 새
`Timer` 하나 또는 `get_tree().create_timer()`로 지연 후 숨김. 이미
있는 "재접속 중..." 배너와 자연스럽게 이어지는 문구라 사용자 입장에서
"재접속 중..." → "복구되었습니다"(3초) → 사라짐의 흐름이 된다.

**하지 않는 것**: 탭이 숨겨지는 시점 감지, 숨겨지는 동안의 안내,
"왜" 끊겼는지(탭 때문인지 네트워크 때문인지)의 구분 표시 - 사용자
입장에서 원인 구분은 중요하지 않고("내가 뭘 했지?"는 스스로 알
가능성이 높음), 복구됐다는 사실 확인만 있으면 충분하다고 판단했다.

### Phase 3 - 낯선 사람 관찰 테스트 (친구 1명, 아무 설명 없이 링크만 전달)

**관찰할 것(개입하지 않고 지켜보기만 - 막히면 그 지점 자체가 데이터)**:
1. **캐릭터를 어떻게 만드는지 알아내는가** - `[캐릭터 선택]`/
   `[캐릭터 관리]` 버튼을 스스로 찾아 누르는지, 이미지/보이스 업로드
   흐름을 설명 없이 따라가는지, 기본 캐릭터로 그냥 시작해버리는지.
2. **방을 어떻게 만들고 초대하는지** - `[방 만들기]`를 찾는지, 인원수
   선택 의미를 이해하는지, 방 코드를 실제로 다른 사람에게 어떻게
   전달하려 하는지(캡처? 그냥 말로 불러줌?).
3. **막히는 지점이 어디인가** - 어느 화면에서 "이걸 왜 눌러야 하는지
   모르겠다"는 반응이 나오는지, 버튼 라벨/배치가 오해를 사는지.
4. **아무 말 없이 기다리게 되는 구간이 있는가** - 특히 첫 접속
   ("서버를 깨우는 중" 문구가 실제로 뜨는지, 그 문구를 보고 기다리는지
   포기하는지), 캐릭터 팩 전송("데이터 수신 중" 단계에서 화면이
   멈춘 것처럼 보이는지), 재접속(끊겼다가 돌아왔을 때 뭔가 표시가
   있었는지 - 위 (C) 구현과 직결).
5. **(추가 권장) 소리 내어 생각하기(think-aloud) 요청** - 가능하면
   "지금 뭘 하려는지, 왜 그 버튼을 눌렀는지" 짧게 말해달라고
   부탁하면 화면만 보는 것보다 훨씬 많은 정보를 얻는다(단, 이러면
   더 이상 "아무 설명 없이"는 아니게 되므로, 순수 관찰과 think-aloud
   두 번을 나눠서 해도 됨).
6. **★ 콜드 스타트 실측(우리가 아직 실측 못 한 것을 여기서 채운다)** -
   친구가 링크를 처음 누를 때 **서버가 잠들어 있는 상태**(위 "운영
   요령"의 미리 깨우기 절차를 일부러 건너뛴 상태)에서 시작해서 기록:
   - 실제로 몇 초 만에 붙는지(스톱워치로 잰다 - Render 공식 안내는
     "50초 이상", 우리 재접속 예산은 최소 95초를 버티도록 확정돼
     있음, 위 참고).
   - 그 동안 화면에 무엇이 보이는지("서버를 깨우는 중입니다(최대
     1분) - 재시도 N/9, X초 후"가 실제로 뜨는지, 1분이 지나도 계속
     갱신되며 남아있는지).
   - **기다리다 포기하지 않는지** - 사람이 실제로 화면에 아무 반응이
     없어 보이면 몇 초 만에 포기하고 탭을 닫는지도 같이 관찰할 것
     (기술적으로 재시도가 계속돼도, 사람이 먼저 포기하면 의미가
     없다 - UX 문제로 별도 취급).
