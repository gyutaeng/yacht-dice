# 캐릭터 팩 포맷 (.ydchar.zip)

1-7에서 도입한, 캐릭터 하나를 파일 하나로 주고받기 위한 포맷이다. 2-5부터는
같은 zip 바이트를 온라인 멀티플레이 로비(`docs/multiplayer.md` §8)에서
실제로 네트워크 청크 전송에도 그대로 쓴다. 포맷을 바꿀 때는 이 문서와
`scripts/characters/character_profile.gd`의 `FORMAT_VERSION`을 같이 갱신할 것.

구현은 `autoload/character_library.gd`의 `export_pack_bytes()` /
`validate_and_extract_pack()` / `import_pack()`에 있다.

## 파일 확장자

`<캐릭터 id>.ydchar.zip` (예: `my-character.ydchar.zip`). 내용물은 표준 ZIP
포맷이라 `.zip`으로 바꿔도 아무 압축 프로그램으로나 열어볼 수 있지만,
`.ydchar.zip`으로 구분해서 사용자가 실수로 다른 zip 파일을 고르지 않게 한다.
가져오기는 확장자가 `.zip`이면 전부 받아준다(실제 스키마 검증은 내용으로 함).

## 폴더 구조

`user://characters/<id>/` 폴더의 내용을 **그 폴더 자체를 감싸지 않고** zip
루트에 그대로 담는다 — 가져올 때 새 id를 발급하므로 원래 폴더 이름(id)을
zip 안에 넣을 이유가 없다.

```
manifest.json          # 필수
portrait.png           # 선택 (manifest.json이 가리킬 때만)
thumb.png              # 선택 (manifest.json의 thumbnail_file이 가리킬 때만)
voices/
  laugh1.wav
  yacht1.wav
  ...
```

**manifest.json이 가리키는 파일만 담는다.** 어디에서도 참조되지 않는 파일은
애초에 `save_profile()`이 저장 시점에 정리하므로(고아 파일 없음), 내보내기는
`manifest.json`이 가리키는 파일 목록을 그대로 zip에 넣기만 하면 된다.
`thumbnail_file`도 빠뜨리지 않고 반드시 포함한다.

## manifest.json 스키마

```json
{
  "format_version": 1,
  "id": "my-character",
  "display_name": "내 캐릭터",
  "portrait_file": "portrait.png",
  "thumbnail_file": "thumb.png",
  "voice_map": {
    "common.my_turn": ["voices/my_turn1.wav"],
    "yacht.yacht": ["voices/yacht1.wav", "voices/yacht2.wav"]
  },
  "volume_db": 0.0
}
```

| 필드 | 타입 | 필수 | 설명 |
|---|---|---|---|
| `format_version` | 정수 | 예 | 지금은 `1`만 유효. 다른 값(모르는 버전)이면 통째로 거부한다. |
| `id` | 문자열 (영숫자+하이픈) | 예 | **가져올 때는 무시되고 항상 새 id가 발급된다** — 원본 폴더 이름일 뿐이다. |
| `display_name` | 문자열 | 예 | 캐릭터 이름. 빈 문자열은 허용(스키마상 문자열이기만 하면 됨). |
| `portrait_file` | 문자열 | 아니오(기본값 `""`) | 프로필 폴더 기준 상대경로. 없으면 초상 없음. |
| `thumbnail_file` | 문자열 | 아니오(기본값 `""`) | 프로필 폴더 기준 상대경로. 없으면 UI가 `portrait_file`로 폴백. |
| `voice_map` | 객체(딕셔너리) | 예(빈 객체 `{}`는 허용) | 이벤트 키 -> 파일명 배열. 파일명은 `voices/`가 아니라 **프로필 폴더 기준** 상대경로(`"voices/xxx.wav"`)로 통일. |
| `volume_db` | 숫자 | 아니오(기본값 `0.0`) | 보이스 재생 볼륨(dB). |

스키마 검증 코드는 `character_profile.gd`의 `from_dict()`를 그대로 재사용한다 —
매니페스트 검증 로직이 export/import 양쪽에서 갈라지지 않는다.

## 검증 규칙 (가져오기 전용 — 신뢰하지 않는 입력)

남이 만든 파일을 여는 기능이므로 아래를 **전부** 통과해야만 디스크에 한
바이트라도 쓴다. 하나라도 걸리면 아무것도 기록하지 않고 한국어 오류 메시지를
돌려준다.

1. **manifest.json 존재 + 스키마** — zip 안에 `manifest.json`이 없거나, 있어도
   `CharacterProfile.from_dict()`를 통과하지 못하면 거부.
2. **경로 안전성(zip slip 방지)** — zip 안의 모든 항목 경로에 대해 다음을
   전부 검사한다. 하나라도 걸리면 거부:
   - `..`이 포함된 경로 (상위 폴더 탈출)
   - 백슬래시(`\`)가 포함된 경로
   - 절대 경로(`/`로 시작하거나 드라이브 문자 등)
3. **확장자 화이트리스트** — 항목 하나라도 아래 목록 밖의 확장자면 zip
   전체를 거부한다: `png`, `jpg`, `jpeg`, `webp`, `wav`, `ogg`, `mp3`, `json`.
4. **압축 해제 크기 상한 50MB** — 항목을 하나씩 읽으면서 누적 압축 해제
   크기를 검사하고, 넘으면 그 자리에서 중단한다(압축률 폭탄 방지). Godot의
   `ZIPReader`는 압축을 풀기 전에 크기만 미리 물어보는 API가 없어서, 항목
   하나가 통째로 거대한 경우 그 항목을 읽는 한 번의 호출 자체가 순간적으로
   메모리를 크게 잡을 수 있다는 한계는 있다 — 다만 "여러 항목의 합이 상한을
   넘는" 흔한 형태의 폭탄은 디스크에 쓰기 전에 막는다.

위 네 가지 검증은 `CharacterLibrary.validate_and_extract_pack(zip_bytes,
yield_node)`라는 순수 함수 하나로 뽑혀 있다(디스크에 아무것도 안 쓰고
zip 바이트를 검증+메모리로 풀어내기만 함) — 로컬 가져오기(`import_pack()`)와
2-5의 네트워크 수신 경로가 이 검증을 공유해서, 신뢰 검증 로직이 두 곳에서
갈라지는 사고를 막는다. `yield_node`를 넘기면 파일을 하나 풀 때마다 한
프레임(`await yield_node.get_tree().process_frame`) 쉰다 — 로컬 가져오기는
사용자가 직접 고른 단발성 동작이라 안 넘기고(즉시 완료), 온라인에서 최대
3명분을 받을 때만 넘겨서 압축 해제가 한 프레임에 몰려 웹 브라우저가
얼어붙는 걸 막는다.

검증을 통과하면(`{"ok": true, "manifest_profile", "extracted"}`) 두
호출부가 서로 다른 곳에 쓴다:

- **로컬 가져오기(`import_pack()`)**: 새 id를 발급하고(`id`가 기존
  캐릭터와 겹치면 `-2`, `-3`처럼 접미사를 붙인다 — **기존 캐릭터를 절대
  덮어쓰지 않는다**) `user://characters/<새 id>/`에 쓰고 사용자 캐릭터
  목록에 편입시킨다.
- **온라인 수신(`ReceivedPackCache.store()`, 2-5)**: 해시를 폴더 이름
  삼아 `user://cache/received/<해시>/`에 쓴다 — `user://characters/`와
  완전히 분리된 자리라 남의 캐릭터가 내 목록에 섞이지 않는다. 자세한
  내용은 `docs/multiplayer.md` §8.4 참고.

manifest.json이 가리키는데 실제로 zip 안에 없는 파일(손상되었거나 다른
도구로 만든 팩)은 캐릭터 전체를 거부하는 대신 그 참조만 조용히 지운다 —
초상/보이스 하나가 없다고 캐릭터 전체를 못 쓰게 할 필요는 없고, 없는
파일은 어차피 게임 쪽 로딩 코드가 폴백 처리를 이미 하고 있다.

## 내보내기 동작

- **데스크톱**: `FileDialog`(저장 모드)로 위치를 물어보고 그 경로에 그대로
  쓴다.
- **웹**: `JavaScriptBridge.download_buffer()`로 브라우저 다운로드를 바로
  일으킨다(저장 위치를 물어보는 절차 없음 — 브라우저가 알아서 다운로드
  폴더에 받는다).
- 내보내기 전에 저장하지 않은 변경사항이 있으면 먼저 저장할지 물어본다.

## 가져오기 동작

- 1-5의 `FilePicker`로 `.zip` 파일을 고른다(데스크톱은 다중 선택 UI라도
  캐릭터 팩은 항상 1개만 받는다).
- 검증을 통과하면 목록을 새로고침하고 새로 들어온 캐릭터를 선택 상태로 만든다.
- 검증에 실패하면 실패 이유를 다이얼로그로 보여주고 아무것도 바꾸지 않는다.

## 업로드 권장 상한 (CharacterLimits)

구현은 `scripts/characters/character_limits.gd`. **`TOTAL_WARNING_BYTES`
(15MB)는 이제 단순 권장이 아니라 2-5의 실제 온라인 전송 하드 캡이다** —
서버(`server_main.gd`)가 소유자가 보낸 `total_bytes`를 이 값과 직접
비교해서 넘으면 전송 자체를 거부한다(`docs/multiplayer.md` §8.3). 편집
화면(1-7B)의 "15MB를 넘으면 온라인에서 전송되지 않을 수 있다"는 안내
문구와 실제 상한이 같은 상수에서 나오므로 서로 어긋날 일이 없다 — 편집
화면에서 업로드하는 순간 막아야 나중에 게임 로비에서 거부당해 편집
화면으로 되돌아오는 왕복이 없다.

| 항목 | 픽셀 상한(긴 변) | 용량 상한 |
|---|---|---|
| 스탠딩(초상) | 2048px | 4MB |
| 썸네일 | 1024px | 1MB |
| 보이스 1개 | (해당 없음) | 1MB, **길이 7초**(아래 참고) |
| 캐릭터 전체 합계 | (해당 없음) | 권장 10MB, 경고 15MB |

### 보이스 길이 제한 (용량과 별개)

용량 제한(1MB)만으로는 길이를 못 막는다 — WAV는 1MB가 대략 11초라
우연히 제한이 되지만, 우리가 OGG/MP3 변환을 권고하는 이유가 바로
"용량이 훨씬 작아진다"는 것이라, OGG 1MB에는 보통 1~2분이 들어간다.

길이 자체가 문제인 이유는 재생 진행 방식 때문이다: `VoiceBank`는 전역으로
한 번에 보이스 하나만 재생하고, 재생 중에 도착한 낮은 우선순위 요청은
`VOICE_WAIT_TIMEOUT_MSEC`(1.5초) 안에 차례가 안 오면 조용히 버려진다
(`autoload/voice_bank.gd`). 대사 하나가 길게 재생되면 그 사이에 일어난
야추·보너스·상대 차례 같은 다른 이벤트의 보이스가 전부 밀려서 버려질 수
있다.

- **하드 상한: 7초**(`CharacterLimits.VOICE_MAX_DURATION_SEC`). 길이는
  `AudioStream.get_length()`로 잰다 - wav/ogg/mp3 전부에서 정확히
  동작함을 실측 확인했다(ffmpeg로 만든 3.7초 파일 세 개, 오차 0).
  넘으면 편집 화면 업로드는 **거부**한다(런타임에 오디오를 잘라낼 수
  없으므로 - 1-7B의 이미지 자동 축소와 달리 "고쳐서 다시 넣기"가
  불가능해서 안내만 하고 막는다). **팩 가져오기(1-7)에서는 거부하지
  않고 경고만 띄운다** - 이미 신뢰 검증을 통과한 팩이라 이제 와서
  거부하지 않는다는 기존 원칙과 같다.
- **이벤트별 권장 길이**(7초는 거부선일 뿐, 적정 길이는 이벤트마다 다름 -
  `GameEvents.VOICE_EVENTS`의 `recommended_label`/`recommended_max_sec`):

  | 이벤트 | 권장 길이 |
  |---|---|
  | 내 차례 | 1~2초 |
  | 포 카드 / 풀 하우스 | 2~3초 |
  | 라지 스트레이트 / 야추 / 상단 보너스 | 3~4초 |
  | 게임 시작 인사 | 5초 이내 |
  | 승리 / 패배 | 7초 이내 |

  권장을 넘어도 거부하지 않는다(7초 안이면 저장됨) - 편집 화면에서
  노란색으로만 표시한다(용량 경고와 같은 색 체계).

**`autoload/asset_loader.gd`의 상한(이미지 8MB, 오디오 2MB)과는 다른 목적이다.**
그건 "이보다 크면 디코딩 자체를 시도하지 않는" 기술적 최후 방어선이고, 위 표는
사용자에게 안내하는 권장 상한이다. 이 표의 값은 항상 `AssetLoader`의 상한보다
작거나 같아야 한다(자동 테스트 `test_character_limits.gd`가 이 관계를
회귀 검증한다).

**픽셀 치수 초과는 경고가 아니라 거부다.** 4096x8192 같은 이미지는 텍스처
메모리를 수백 MB 잡아먹어서 특히 웹에서 치명적이기 때문이다. 용량(바이트)
초과도 거부되지만, 두 종류의 거부는 대응 방법이 다르다:

- **픽셀 치수 초과**: `Image.resize()`로 자동 축소해서 다시 넣을지 물어본다
  (원본 비율 유지, `Image.INTERPOLATE_LANCZOS`, 원본 확장자 그대로 재인코딩 -
  PNG는 무손실, JPG/WebP는 품질 0.9). 자동 축소 후에도 한도를 넘으면(드묾)
  그때는 그냥 거부한다.
- **용량만 초과(치수는 정상)**: 자동 축소를 제안하지 않는다 — 이미 작은
  치수를 더 줄이면 화질만 나빠지고 원인(비효율적인 포맷)은 해결되지 않는다.
  대신 WebP 변환 등을 안내만 한다.

### 안내 문구 형식

거부 메시지는 항상 세 가지를 한 번에 알려준다: **지금 얼마인지 -> 한도가
얼마인지 -> 어떻게 줄이는지.** "용량이 큽니다"처럼 원인만 말하고 해결법을
안 알려주는 메시지는 쓰지 않는다.

이미지가 클 때:
> 이 이미지는 3840x5120, 12.4MB입니다. 스탠딩은 긴 변 2048px, 4MB까지
> 넣을 수 있어요. 크기를 줄이거나 WebP로 저장하면 훨씬 작아집니다.
> (투명 배경이 필요하면 PNG 대신 WebP를 쓰세요. 보통 1/3~1/5로 줄어듭니다)

오디오가 클 때:
> 이 파일은 3.2MB입니다. 보이스 하나는 1MB까지 넣을 수 있어요.
> WAV는 압축이 없어서 큽니다. OGG나 MP3로 변환하면 보통 10배 작아집니다.

WAV를 올렸는데 한도 안에 들어와도(거부가 아니라 권고), 온라인 전송을
염두에 둔 가벼운 안내가 따라온다:
> WAV 파일이에요. OGG나 MP3로 바꾸면 훨씬 작아져서 나중에 온라인에서
> 캐릭터를 주고받을 때 유리합니다.

### 캐릭터 전체 합계 표시

편집 화면 상단에 "현재 캐릭터 용량: 3.2MB / 15MB"가 항상 떠 있다
(`CharacterLibrary.compute_pack_size()`가 manifest가 가리키는 파일들의
디스크 상 크기를 더해서 계산 - 아직 저장 전이어도 방금 올린 파일은 이미
디스크에 쓰였으므로 실시간으로 정확하다). 10MB를 넘으면 노란색, 15MB를
넘으면 빨간색으로 표시가 바뀐다. **15MB를 넘어도 저장 자체는 막지 않는다** -
다만 저장할 때마다 "온라인에서 상대에게 전송되지 않을 수 있습니다"를
분명히 알려준다.

### 가져오기에도 같은 기준 적용 (거부 아님 - 경고만)

1-7의 팩 가져오기가 이미 통과한(신뢰 검증 완료) 캐릭터에 대해서도 같은
`CharacterLimits` 기준으로 다시 검사하지만, 여기서는 절대 거부하지 않는다 -
남이 이미 만든 파일이니 못 쓰게 막을 이유가 없다. 초상/썸네일/보이스 중
한도를 넘는 게 있거나 전체 합계가 15MB를 넘으면, 가져오기는 그대로
완료시키되 어떤 파일이 얼마나 넘었는지 알려주는 안내 다이얼로그를 띄운다
(`CharacterLibrary.import_pack()`이 반환하는 `warning` 필드).

### 이미지 자동 축소를 넣은 이유 (검토 결과)

거부만 하면 사용자는 "다른 파일을 만들어서 다시 오세요"를 들어야 한다.
`Image.resize()` + 원본 포맷 재인코딩은 이미 로드해서 갖고 있는 `Image`
객체에 한 번의 호출만 추가하면 되는 정도라 구현 비용이 낮고, 원본 비율을
유지한 채 Lanczos 보간으로 줄이므로 화질 저하도 일반적인 다운스케일
수준으로 허용할 만하다고 판단해 넣었다. 오디오는 런타임에서 재인코딩할
방법이 없어서(디코더는 있어도 인코더가 없음) 안내만 한다.
